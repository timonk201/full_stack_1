### Недоделки, найденные тестами

- В каталогах нет товаров в новой базе — тесты показали пустое состояние и заставили проверить и заполнить локальную PostgreSQL.
- Поля авторизации и заявки имеют похожую подпись Email — локаторы стали использовать конкретную форму через `getByRole('form', { name: 'Вход' })`.

- Каталог уже поддерживает состояния загрузки, пустого каталога и ошибки загрузки с `role="status"` и `role="alert"`.
- Для формы входа реализована блокировка повторной отправки с состоянием загрузки.

### Почему MSW и когда нужен реальный API

MSW перехватывает HTTP-запросы уровня сети и возвращает детерминированные ответы, поэтому компонентные тесты не зависят от PostgreSQL и скорости локального сервера. Это лучше простого `vi.mock(fetch)`, потому что компонентный код продолжает выполнять обычный `fetch` и обрабатывать реальные HTTP-статусы. Реальный Express-сервер и PostgreSQL нужны для E2E-тестов и проверки интеграции.

### Smoke против production

Полные E2E создают записи в базе, поэтому их нельзя запускать против production: тест регистрации изменит данные и может повлиять на лимитер или реальных пользователей. Smoke-тесты выполняют только чтение и проверяют доступность каталога и фильтрацию без изменения данных.

`E2E_BASE_URL=https://ваш-сайт.vercel.app npm run e2e:smoke`

### Цена -500

Поле имеет HTML-атрибут `min="0"`, поэтому браузер не должен отправить явно отрицательное значение обычным сабмитом формы. Сервер дополнительно проверяет значение Zod и должен вернуть HTTP 400 с `details`, например `{ field: "price", message: "Цена должна быть больше 0" }`. Обе проверки нужны: браузер даёт быструю обратную связь пользователю, а сервер защищает API от прямых запросов и обхода интерфейса.

### Ответы для защиты

**Чем компонентный тест отличается от E2E-теста?**
Компонентный тест рендерит часть React-приложения в jsdom и проверяет изолированную функциональность или подменённый API. E2E запускает настоящий Chromium и проверяет взаимодействие браузера, frontend, backend и базы данных целиком.

**Что такое пирамида тестов?**
Это подход с большим количеством быстрых и дешёвых модульных/компонентных тестов, меньшим числом интеграционных тестов и ещё меньшим числом медленных E2E-тестов.

**Что делает jsdom?**
jsdom предоставляет DOM и APIs Node-окружения вроде `document`, `window` и `localStorage`. В jsdom нет настоящего layout-движка и реальной вкладки браузера; Playwright нужен для реального рендера и пользовательских сценариев.

**Почему ищут элементы по роли и подписи?**
Роль и доступная подпись описывают интерфейс так, как его воспринимает пользователь и assistive-технологии. Классы CSS и test-id могут меняться при редизайне и не проверяют доступность.

**Чем отличаются getBy, queryBy и findBy?**
`getBy` сразу ищет ровно один элемент и падает, если нет или несколько совпадений. `queryBy` возвращает `null` и нужен для проверки отсутствия элемента. `findBy` ждёт асинхронное появление элемента.

**Что делает resetHandlers и localStorage.clear()?**
`resetHandlers()` отменяет подмены конкретного теста и возвращает стандартные MSW-handlers. `localStorage.clear()` удаляет токен и данные предыдущего теста. Без очистки результаты тестов станут зависимыми друг от друга.

**Что такое автоожидание в Playwright?**
Playwright повторно проверяет locator до таймаута и сам ждёт кликабельность элемента. `waitForTimeout(3000)` создаёт фиксированную задержку и не гарантирует готовности нужного элемента, поэтому лучше использовать `expect(locator)...` или другое состояние UI.

**Почему в E2E используется e-mail с Date.now()?**
Регистрация создаёт реального пользователя в базе. Уникальный адрес позволяет повторно запускать тест и избежать ошибки duplicate e-mail. Без уникального адреса второй запуск может быть отклонён сервером.

**Почему полные E2E нельзя запускать на production?**
Регистрация, покупки и заявки изменяют production-базу. Smoke-тест должен только читать и проверять доступность. Запускать его следует после деплоя, по расписанию или вручную.

**Что делать при внезапном 429?**
Нужно перезапустить локальный API, если счётчик лимитера хранится в памяти, или отделить unit/MSW-тесты от реального лимитера. Повторяющиеся login-попытки лучше тестировать через отдельные сценарии и не выполнять без необходимости в цикле.

**Зачем npm run build в CI?**
Сборка ловит ошибки импортов и production-конфигурации, которые Vitest или dev-сервер могут пропустить. Она также проверяет, что приложение действительно собирается перед merge/deploy.

**Что даёт Require status checks to pass?**
Запрет merge до успешного прохождения обязательных GitHub Actions-проверок. Обход возможен только через администрирование репозитория или переопределение настроек ветки; это не должно использоваться для мерцания красного CI.

**Почему тест проходит локально, но падает в CI?**
Возможны: другие переменные окружения или API URL, Linux-регистр файлов вместо Windows, отсутствие базы/секретов или зависимость от реального состояния базы. В CI нужно смотреть полный лог, environment, artifact и Playwright trace.
